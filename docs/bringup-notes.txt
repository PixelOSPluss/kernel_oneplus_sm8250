  Symptom:

    '__crc_copy_page'; recompile with -fPIC

  What we verified / tried:
  - Happens with LTO off. Config now: MODVERSIONS=y, TRIM_UNUSED_KSYMS off,
    RELOCATABLE=y (selected by RANDOMIZE_BASE=y), HAVE_ARCH_PREL32_RELOCATIONS=y,
    MODULE_REL_CRCS OFF (reverted).
  - Tried CONFIG_MODULE_REL_CRCS=on (via Kconfig select) -> same link failure but
    with R_AARCH64_PREL32 instead of ABS32. REVERTED. Both ABS32 and PREL32 fail,
    so the relocation TYPE is not the deciding factor.
  - Tried -pie (Xiaomi original LLD flag) and -shared (OnePlus flag): both fail.
  - Tried removing KONA "-mllvm -mcpu=cortex-a55" KBUILD_LDFLAGS: still fails.

  KEY DIAGNOSTIC FINDING (why OnePlus links but we don't):
  - In OUR objects (e.g. out-kebab/arch/arm64/lib/memset.o) the assembly
    EXPORT_SYMBOL creates ___kcrctab+xxx sections with R_AARCH64_ABS32
    relocations against __crc_xxx, and __crc_xxx shows as WEAK UNDEFINED
    (nm: " w __crc_memset"). The per-object modversions genksyms .ver relink
    (cmd_modversions_c) does NOT appear to have resolved these to strong ABS.
  - In the OnePlus reference build, arch/arm64/lib/memset.o has NO ___ksymtab /
    ___kcrctab / __ksymtab_strings sections and NO __crc_* symbols at all.
    memset is instead exported from lib/string.o (nm vmlinux shows __ksymtab_memset
    lives at ffffff8012921bb0, defined in lib/string.o). OnePlus vmlinux has
    __crc_memset etc. as absolute symbols (A) and linked fine.
  - Root difference: Xiaomi arch/arm64/lib/memset.S (and other *.S) contain
    EXPORT_SYMBOL(memset)/EXPORT_SYMBOL(__memset) at lines ~218-220; OnePlus
    arch/arm64/lib/memset.S has NO EXPORT_SYMBOL at all.
  - Because these are WEAK UNDEFINED __crc_* references, LLD treats them as
    preemptible in the -shared/-pie link and rejects the ABS32 (and PREL32)
    relocations -> "recompile with -fPIC".

  ROOT CAUSE of the original link failure (FOUND):
  - Xiaomi's arch/arm64/lib/*.S and arch/arm64/kernel/smccc-call.S carry
    EXPORT_SYMBOL/EXPORT_SYMBOL_NOKASAN for 17 arch symbols. In our LLD
    -shared link the resulting ___kcrctab R_AARCH64_ABS32 relocations target
    __crc_* symbols that are WEAK-UNDEFINED (modversions .ver relink never
    resolves assembly exports), so LLD treats them as preemptible and aborts
    with "relocation R_AARCH64_ABS32 cannot be used against symbol
    '__crc_*'; recompile with -fPIC".
  - OnePlus never hits this: its objects carry NO export sections; all arch
    exports live in arch/arm64/kernel/arm64ksyms.c (C -> modversions resolves
    __crc_* to strong ABS, which LLD accepts).

  THE FIX (mirrors OnePlus):
  1. arch/arm64/kernel/arm64ksyms.c — added exports (moved from ASM):
     copy_page, clear_page, __arch_copy_from_user/__arch_copy_to_user/
     __arch_clear_user/__arch_copy_in_user, strchr, strrchr, strcmp, strncmp,
     strlen, strnlen, memcmp, memchr, memset, memcpy, memmove, __memset,
     __memcpy, __memmove, __arm_smccc_smc, __arm_smccc_hvc,
     __ashlti3, __ashrti3, __lshrti3 (+ #include <linux/string.h>,
     <linux/uaccess.h>, <linux/arm-smccc.h>). NOT added: bitops (Xiaomi/OnePlus
     both use asm-generic inline, cannot export), _mcount (FUNCTION_TRACER off),
     memstart_addr, strlen/strncmp/memcmp had to stay C-exported only (lib/
     string.c guards on __HAVE_ARCH_* are NOT set for them since the .S files
     existed -> they moved to arm64ksyms.c too).
  2. Stripped EXPORT_SYMBOL(_NOKASAN) from 18 ASM files:
     arch/arm64/lib/{clear_page,copy_from_user,copy_page,tishift,memcpy,
     copy_to_user,clear_user,copy_in_user,memset,memchr,strchr,strcmp,strnlen,
     strrchr,strncmp,memcmp,strlen}.S + arch/arm64/kernel/smccc-call.S.
     C-object exports in arch/arm64/lib/{delay,csum,xor-neon,uaccess_flushcache}
     .c are unaffected (modversions resolves them fine).
